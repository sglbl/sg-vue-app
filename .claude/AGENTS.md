
Our purpose is to use these 3 to complement each other and stay away from manually edited migration files.
- **supabase cli** : install with brew
- **srtd** : postgres functions + rls + extensions (idenpotent) use [skill](.claude/skills/srtd-cli/SKILL.md)
- **declaritive schemas** : tables, use [skill](skills/declarative-schema/SKILL.md)

- Check `.claude` folder for rules and skills related to those.
- Check `docs/` folder for related documentation.

## Database workflow rules — one source of truth per file type

Each tool owns one level. **Never** mix them — that's why we have three.

| What | Where it's declared | Tool that owns it | Migration file generated by |
|---|---|---|---|
| Tables, columns, indexes, **GRANTs**, `ENABLE ROW LEVEL SECURITY`, CHECK constraints | `supabase/schemas/*.sql` | declarative schemas | `supabase db diff -f <name>` |
| RLS policies, functions, views, extensions | `supabase/migrations-templates/*.sql` | srtd | `srtd build` |

**Hard rules:**

1. **Never hand-write a migration.** Every file in `supabase/migrations/` is generated — by `supabase db diff` for schema changes, by `srtd build` for srtd changes. If you find yourself typing `CREATE TABLE`, `CREATE POLICY`, or `GRANT` into a migration file, stop and update the schema or srtd template instead.
2. **Never hand-edit the schema or srtd template just to avoid running their tools.** Both flows are idempotent and safe to re-run.
3. **`supabase db diff` may emit false-positive `DROP POLICY` statements** because it doesn't know policies are owned by srtd. These are tool output, not source-of-truth edits — they may be removed from the generated migration with a comment explaining why. Never ADD to a migration by hand; only remove lines the diff emitted.

## Frontend
- **Vue 3 + Vite + TypeScript** in `src/`
- **Pinia** for state — Composition API style only (`defineStore('id', () => {...}, { persist })`)
- **@supabase/supabase-js** for the cloud backend (lesson 13+)
- **No Options API anywhere.** Components, stores — all Composition API.
- Stores live in `src/stores/`, components in `src/components/`, views in `src/views/`.
