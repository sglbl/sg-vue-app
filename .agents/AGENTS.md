Our purpose is to use modern Supabase declarative schemas to stay away from manually edited migration files.
- **Supabase CLI** : install with brew
- **Declarative Schemas (`pg-delta`)** : tables, RLS policies, functions, views, triggers, and grants in `supabase/database/`, use [skill](skills/declarative-schema/SKILL.md)

- Check `.claude` folder for rules and skills.
- Check `docs/` folder for related documentation.

## Database workflow rules — Declarative schemas as single source of truth

`supabase/database/` is the single source of truth for your database schema.

| What | Where it's declared | Tool that owns it | Migration file generated by |
|---|---|---|---|
| Tables, columns, indexes, constraints, GRANTs, RLS policies, functions, views, triggers | `supabase/database/**/*.sql` | Supabase Declarative Schemas (`pg-delta`) | `supabase db schema declarative sync -f <name>` |

**Hard rules:**

1. **Never hand-write a migration.** Every file in `supabase/migrations/` is generated by `supabase db schema declarative sync`. If you find yourself typing `CREATE TABLE`, `CREATE POLICY`, or `GRANT` into a migration file, stop and update the declarative files under `supabase/database/` instead.
2. **Never change schema directly in Studio/SQL Editor.** `supabase db schema declarative sync` diffs the declarative schema files against migration history (not the live DB). Changes made directly in Studio or psql will be missed.
3. **Always generate migrations using `supabase db schema declarative sync -f <name>`**, then review the generated migration before applying (`supabase migration up` or `--apply`).

## Frontend
- **Vue 3 + Vite + TypeScript** in `src/`
- **Pinia** for state — Composition API style only (`defineStore('id', () => {...}, { persist })`)
- **@supabase/supabase-js** for the cloud backend (lesson 13+)
- **No Options API anywhere.** Components, stores — all Composition API.
- Stores live in `src/stores/`, components in `src/components/`, views in `src/views/`.
